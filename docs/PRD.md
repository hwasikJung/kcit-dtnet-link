## 1. 개요

### 1.1 목적
Swagger UI처럼 API를 직접 호출하고 그 결과(JSON)를 확인할 수 있는 웹 사이트를 제작한다.
단, **대상 사용자가 비개발자**이므로 Swagger UI보다 훨씬 단순하고 직관적인 UI/UX를 제공하는 것이 핵심 목표다.

### 1.2 배경
대상 API 서버는 SQI Soft의 **주소 정제/매칭/지오코딩 API**다. 현재는 표준 Swagger UI(`http://220.76.251.227:9930/api-docs/`)로만 노출되어 있어, 비개발자가 파라미터 구조·스키마·태그 등 개발자 친화적 화면을 이해하기 어렵다.
본 프로젝트는 이 API를 "주소 한 줄 입력 → 버튼 클릭 → 결과 확인" 수준으로 단순화한 전용 테스트 콘솔을 만든다.

### 1.3 범위
- 포함(In-scope): 메뉴 2개로 구성된 SPA 웹 사이트, 메뉴1(API 테스터), 메뉴2(엑셀 기반 건물 정보 일괄 조회 — **PostgreSQL 직접 조회**), CORS 회피용 서버 프록시, PostgreSQL 읽기 전용 연동.
- 제외(Out-of-scope): 로그인/로그아웃/회원 등 인증 기능(요구사항상 불필요), API 서버 자체 수정, DB에 대한 쓰기/저장(조회 전용).

### 1.4 대상 사용자
- 주 사용자: **비개발자**(내부 운영/기획/데이터 담당자 등). API 호출·JSON에 익숙하지 않음.
- 부 사용자: 개발자(빠른 API 동작 확인 용도).
- 설계 원칙: 사용자는 "주소 문자열"만 알면 되고, HTTP 메서드·경로·스키마는 몰라도 사용할 수 있어야 한다.

### 2.4 스펙에서 도출한 설계적 시사점
1. **파라미터 패턴이 단순**하다. 26개 중 대다수가 `input_addr` 하나만 받으므로, 비개발자용 UI로 추상화하기 매우 유리하다("주소 입력 → 실행").
2. **응답 스키마 정의가 없다**(`components.schemas` 비어 있음). 응답은 자유 형식 JSON이므로, 결과 화면은 **범용 JSON 뷰어**로 처리해야 한다(고정 테이블 렌더링 불가).
3. **`(수정예정)`, `(삭제예정)` 태그가 붙은 엔드포인트**가 있다(건물매칭 일부, 에너지매칭 전체). **[확정] 목록에 노출하되 배지(예: "수정예정"/"삭제예정")로 구분 표시**한다 — 숨기지 않는다.
4. **TTA만 CSV 업로드(POST)** 이고 EUC-KR 인코딩·고정 컬럼을 요구한다. 파일 업로드 UI가 별도로 필요하다(메뉴1 파라미터 폼에서 처리).
5. **HTTP(비 TLS) + servers 미정의**. 브라우저에서 직접 호출 시 CORS 및 Mixed Content(HTTPS 사이트에서 HTTP 호출 차단) 문제가 발생하므로 **서버 프록시가 사실상 필수**다(→ 6장).

## 3. 기능 요구사항

### 3.1 전체 구조 — 2개 메뉴
| 메뉴 | 명칭(안) | 우선순위 | 상태 |
|---|---|---|---|
| 메뉴 1 | API 테스트 콘솔 | P0 (핵심) | 확정 |
| 메뉴 2 | 엑셀(mgmBldPk) 일괄 조회 — PostgreSQL 직접 조회 | P1 | **방식 확정** (조회 테이블/스키마 미정) |

상단 또는 좌측에 2개 메뉴 네비게이션. 인증 없음 → 진입 즉시 사용 가능.

### 3.2 메뉴 1 — API 테스트 콘솔 (핵심)

Swagger의 좌우 분할 패턴을 계승하되 단순화한다.

**레이아웃: 좌우 2분할**
- **좌측(호출 영역):** API 목록 + 파라미터 입력 + 실행 버튼
- **우측(결과 영역):** 응답 JSON 표시

**F-1. API 목록/선택 (좌측 상단)**
- 9개 태그로 그룹핑된 API 목록을 아코디언 또는 그룹 리스트로 표시.
- 각 항목은 개발자 용어(GET/POST, 경로) 대신 **한국어 요약(summary)** 을 1차 노출한다. 예: "주소 정제 (실제 주소 매칭으로 정제)". 메서드/경로는 보조 정보로 작게 표기.
- 검색 박스로 API 이름 필터링(비개발자가 "정제", "좌표" 등 키워드로 탐색).
- **[확정] `(수정예정)`/`(삭제예정)` API는 목록에 노출하되 배지로 구분 표시**한다. summary 문구의 `(수정예정)`·`(삭제예정)` 접두를 파싱해 상태 배지(예: 회색 "수정예정", 적색 "삭제예정")로 렌더링하고, 본문 요약에서는 접두 표기를 제거해 가독성을 높인다. 배지에는 tooltip로 "향후 변경/폐기 예정 API" 안내.

**F-2. 파라미터 입력 (좌측 중단)**
- 선택한 API의 파라미터를 **자동 폼 생성**한다(스펙 기반 동적 렌더링).
  - `input_addr` → 텍스트 입력(가장 흔함). placeholder에 예시 주소 제공.
  - path 파라미터(`{pnu}`, `{mgmbldpk}` 등) → 개별 입력 필드.
  - boolean 옵션(`isRemoveNextLine` 등) → 체크박스/토글.
  - 좌표변환 4개 필드(`src/dst/x/y`) → 각 입력 필드(가능하면 `src/dst`는 좌표계 선택 드롭다운).
  - TTA → 파일 업로드 컴포넌트(CSV, EUC-KR 안내 문구 포함).
- 필수 파라미터 미입력 시 실행 버튼 비활성화 + 안내.

**F-3. 실행 (좌측 하단)**
- "실행"(호출) 버튼 1개. 클릭 시 서버 프록시를 통해 대상 API 호출.
- 로딩 상태 표시(스피너), 소요 시간(ms) 표시.

**F-4. 결과 표시 (우측)**
- 응답 JSON을 **가독성 좋은 JSON 뷰어**로 표시(구문 강조, 접기/펼치기, 들여쓰기).
- HTTP 상태코드 + 성공/실패 배지(2xx 녹색, 4xx/5xx 빨강).
- "복사"(Raw JSON 복사) 버튼, "펼치기/접기" 토글.
- 오류 시 사용자 친화적 메시지(예: "요청에 실패했어요. 주소를 다시 확인해 주세요.") + 원문 오류 접이식 표시.
- (옵션) 호출한 실제 URL/cURL 표시 → 개발자용 보조.

**F-5. (제안) 최근 호출 히스토리**
- 세션 내에서 최근 호출한 API·파라미터·결과를 리스트로 유지(브라우저 로컬 저장). 비개발자가 이전 결과와 비교하기 쉬움. — 채택 여부 미확정.

**F-6. (Backlog) 좌표 결과 지도 미리보기**
- 응답에 위경도(x/y)가 포함된 경우 지도에 표시하는 기능은 이번 범위에서 제외하고 향후 확장(5.2 Backlog)으로 남긴다.

### 3.3 메뉴 2 — 엑셀 기반 건물 정보 일괄 조회 (방식 확정)

엑셀 A열에 `mgmBldPk`(건축물대장 PK) 목록을 담아 업로드하면, **PostgreSQL에서 해당 PK의 건물 정보를 직접 조회**해 그 결과를 **B열부터 컬럼으로 병합**해 보여주는 화면이다. 데이터 소스는 API가 아니라 DB다(v1.2 확정). **조회 대상 테이블/컬럼 스키마는 미확정**(8.2)이며, 처리 방식(업로드 → 일괄 조회 → 목록 표시 → Modal 상세)은 확정이다.

**흐름 요약**
```
엑셀 업로드(A열 = mgmBldPk) → A열 목록을 서버로 전달 → Nitro server route가 PostgreSQL 일괄 조회
→ B열~N열에 조회 데이터 병합 → 웹 화면에 결과 목록 테이블 표시 → 행 클릭 시 Modal로 상세 정보 표시
```

**E-1. 엑셀 업로드**
- xlsx 업로드(필요 시 csv 병행). **A열 = `mgmBldPk`** 규칙. 1행 헤더 유무는 자동 감지 또는 양식 안내(8.2).
- 업로드 즉시 A열 목록을 테이블로 표시(호출 전 상태). 유효성 검사(빈 값/중복/형식) 결과 표시.

**E-2. 일괄 DB 조회**
- A열 목록을 서버 route(예: `POST /api/bld/lookup`)로 전달하면, 서버가 PostgreSQL에서 `WHERE mgm_bld_pk = ANY($1)` 방식으로 **일괄 배치 조회**한다(대량이면 청크 분할, 파라미터 바인딩 필수 — SQL 인젝션 방지).
- 진행률(청크 n/전체)과 행별 상태(성공 / **미존재** / 실패) 표시. DB에 없는 PK는 "미존재"로 구분 표시.
- **조회 대상 테이블/컬럼은 미확정**(8.2). 확정 전까지 조회 쿼리를 서버 설정/단일 모듈로 분리해 교체가 쉽게 설계한다(하드코딩 금지). DB 접근은 **읽기 전용**(SELECT만).

**E-3. 결과 컬럼 병합 (B열~)**
- 조회 결과의 컬럼을 **B열부터 순서대로 추가**한다. DB 테이블 스키마가 곧 컬럼 정의이므로 API 응답 flatten 대비 매핑이 단순하다. 표시 컬럼 선정·순서·한글 컬럼명 매핑은 스키마 확인 후 결정(8.2).

**E-4. 결과 목록 테이블 (웹 화면)**
- 업로드·호출 결과가 병합된 목록을 웹 페이지 테이블로 표시(A열 + 추가된 컬럼).
- 컬럼이 많을 경우 가로 스크롤 + 주요 컬럼 우선 표시. 행이 많을 경우 페이지네이션 또는 가상 스크롤.

**E-5. 행 클릭 → Modal 상세**
- 행 클릭 시 **Modal(다이얼로그)** 로 해당 행의 추가된 정보 전체를 표시.
- 필드명/값 표 형태 기본 + 원본 JSON 접이식 표시(메뉴1 JSON 뷰어 컴포넌트 재사용).

**E-6. (제안) 결과 엑셀 다운로드**
- 병합 완료된 데이터(A열 + B열~)를 xlsx로 다운로드. — 채택 여부 미확정(8.2).

**엑셀 처리 기술 검토는 6.4 참조.**

**대안 검토:** 순수 정적 HTML/JS(참고 프로젝트의 `public` 정신)로도 가능하나, (a) CORS/Mixed Content 프록시를 위해 어차피 서버 런타임이 필요하고, (b) 동적 폼 생성·JSON 뷰어·컴포넌트 재사용 측면에서 Nuxt가 유리하므로 Nuxt를 권장한다.

### 6.2 CORS / Mixed Content 이슈 (중요)
브라우저에서 `http://220.76.251.227:9930`을 직접 호출할 경우 2가지 문제:
1. **CORS**: 대상 서버가 `Access-Control-Allow-Origin`을 우리 사이트 Origin으로 허용하지 않으면 브라우저가 응답을 차단.
2. **Mixed Content**: 본 사이트를 HTTPS로 배포하면, HTTP(비 TLS) API 직접 호출이 브라우저에 의해 차단됨.

→ 두 문제 모두 **동일 출처 서버 프록시**로 해결한다.

### 6.3 프록시 설계 (권장 아키텍처)
```
[브라우저] --(same-origin, HTTPS)--> [우리 Nuxt/Nitro 서버 프록시] --(HTTP)--> [220.76.251.227:9930 API]
   /api/proxy/addr/...  (동일 출처, CORS 무관)         서버 간 호출은 CORS 미적용
```
- Nitro `server/api/proxy/[...].ts`에서 대상 Origin(고정 화이트리스트)으로 요청을 포워딩.
- 브라우저는 항상 동일 출처(`/api/proxy/...`)만 호출 → CORS·Mixed Content 모두 회피.
- 파일 업로드(TTA multipart)와 EUC-KR 응답 인코딩도 서버 프록시에서 안전하게 중계.
- 보안: 프록시 대상 Origin을 환경변수로 **고정**(임의 URL 프록시 금지 → SSRF 방지).

> 대안: 개발 편의상 Nuxt `routeRules`/`nitro.devProxy` 또는 Vite dev proxy로 개발 시 CORS 우회 가능. 운영은 위 명시적 프록시 라우트 권장.

> **[확정] 배포 환경 미정에 대비**해, 위 Nitro server route 프록시를 **기본 구성으로 포함**한다. HTTPS 배포/사내망/정적 호스팅 등 어떤 환경에서도 브라우저는 동일 출처(`/api/proxy/*`)만 호출하므로 CORS·Mixed Content 문제가 발생하지 않는다. (정적 전용 호스팅으로 배포할 수 없다는 제약이 생기지만, 프록시 필요성상 서버 런타임 채택이 타당.)

### 6.4 엑셀 처리 · DB 조회 기술 검토 (메뉴 2)

| 항목 | 방안 | 비고 |
|---|---|---|
| 업로드 파싱 | **SheetJS(xlsx)** — 클라이언트 파싱 | xlsx/csv 지원. 브라우저에서 A열(`mgmBldPk`)만 추출해 서버로 전달(파일 자체 업로드 불필요) |
| 일괄 조회 | Nitro server route → **PostgreSQL `WHERE mgm_bld_pk = ANY($1)` 배치 조회** | 청크 분할(예: 500건/쿼리), 파라미터 바인딩(SQL 인젝션 방지), 읽기 전용 계정 권장 |
| DB 커넥션 | `pg` 커넥션 풀(서버 기동 시 1회 생성, Nitro plugin/유틸 싱글톤) | 접속 정보는 `runtimeConfig` + 환경변수 |
| 결과 병합 | 조회 결과 컬럼 → 테이블 컬럼(B열~) | 표시 컬럼 선정·한글 컬럼명 매핑은 스키마 확인 후 정의(8.2) |
| 다운로드(제안) | SheetJS로 병합 결과 xlsx 생성 | 채택 여부 미확정(8.2) |

> 대량 행 처리 시 1회 업로드 처리 상한(예: 10,000행)과 쿼리 청크 크기를 두는 것을 권장 — 상한값은 미확정(8.2). DB 배치 조회는 행별 API 호출 대비 수십 배 빠르므로 상한을 넉넉히 잡을 수 있다.

### 8.2 잔여 미확정 (구현 전/중 확인 필요)
1. **대상 API 서버 접근성**: `220.76.251.227:9930`이 운영 중 항상 접근 가능한 고정 IP인지, **인증키가 추후 추가될 예정**인지. (프록시 인증 헤더 처리 여부에 영향)
2. **메뉴2 DB 조회 대상**: PostgreSQL의 **접속 정보(호스트/포트/DB명/계정 — 읽기 전용 계정 권장)** 와 **조회 대상 테이블/컬럼 스키마** 미정. 확정 전까지 조회 쿼리를 설정/단일 모듈로 분리해 대비.
3. **메뉴2 엑셀 양식**: 1행 헤더 유무, A열 외 컬럼 허용 여부, 표준 양식(템플릿) 다운로드 제공 여부.
4. **결과 컬럼 매핑 규칙**: 표시 컬럼 선정·순서·한글 컬럼명 매핑(테이블 스키마 확인 후 정의).
5. **처리 상한**: 1회 업로드 최대 행 수, 쿼리 청크 크기, 결과 엑셀 다운로드(E-6) 채택 여부.
6. **TTA CSV 업로드** 메뉴1 파라미터 폼에서의 지원 범위(단순 업로드/결과 표시 수준).
7. **결과 저장/히스토리(F-5)** 필요 여부(로컬 저장 vs 서버 저장). 서버 저장 시 DB 도입 필요.
8. **스펙 갱신 방식**: 표준 스펙 엔드포인트(`/v3/api-docs` 등) 부재 → API 목록을 (a) `swagger-ui-init.js`에서 주기적 자동 추출 / (b) 최초 1회 스냅샷 후 수동 관리 중 선택.
